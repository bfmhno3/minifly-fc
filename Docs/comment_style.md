# 项目注释规范指南

本规范旨在建立清晰、务实的代码注释标准，降低代码的维护成本和开发者的心智负担。

## 1. 核心理念 (Core Philosophy)

- **Why over How:** 代码本身负责说明 “怎么做 (How)”，注释负责解释 “为什么这么做 (Why)”。
- **参考业界标杆:** 
  - **[Linux Kernel Coding Style (Chapter 8)](https://www.kernel.org/doc/html/latest/process/coding-style.html#commenting):** 不要过度注释糟糕的代码，重写它。注释应该解释代码的大致意图和原因，而不是解释具体的 C 语法。
  - **[Google C++ Style Guide (Comments)](https://google.github.io/styleguide/cppguide.html#Comments):** 必须对实现细节中的 “巧妙的、晦涩的或反常识的” 逻辑加以解释，消除后续维护者的困惑。


## 2. 函数头注释 (Doxygen 规范)

函数头注释采用精简版 Doxygen 格式。坚决废弃 `@author`, `@date`, `@version` 等历史遗留标签，版本与追溯信息统一交由 Git 管理。

### 2.1 标签使用分级

- **核心必填项:**
  - `@brief`: 一句话简述函数功能。
  - `@param`: 参数描述。**必须**包含方向标志 `[in]`, `[out]`, 或 `[in,out]`，明确指针行为。
  - `@return`: 返回值通用含义描述。
- **硬件/底层开发按需项:**
  - `@retval`: 专门用于枚举值或特定错误码的返回说明。
  - `@warning` / `@attention`: 标记物理雷区或致命错误（如死区时间配置、中断阻塞操作等）。
  - `@pre`: 前置条件（调用前系统必须处于的状态）。
- **模块化组织 (用于头文件):**
  - `@defgroup` / `@addtogroup`: 用于将相关的宏、枚举和 API 函数打包成一个清晰的模块文档目录。

### 2.2 规范模板示例

```c
/**
 * @brief  启动死区时间受控的 H 桥驱动输出
 * 
 * @pre    必须已完成 PWM 定时器和死区寄存器的初始化
 * @param[in]  duty_cycle  目标占空比 (0.0 到 1.0)
 * @param[out] status_flag 指向状态标志位的指针，用于回传硬件错误
 * 
 * @retval 0  驱动成功启动
 * @retval -1 参数越界，已被钳位限制
 * 
 * @warning 占空比突变过大可能导致电流过冲，需配合外部限流电路
 */
int start_hbridge_drive(float duty_cycle, uint8_t *status_flag);
```

## 3. 函数内部注释 (5 条铁律)

函数内部的注释应极度克制且精准，遵循以下规范：

**规则 1：解释 “为什么 (Why)”，绝不翻译代码 (How)**

- ❌ 错误：`a = a << 1; // 将 a 左移一位`
- ✅ 正确：`a = a << 1; // 乘以 2 以匹配硬件预期的时钟周期`

**规则 2：揭示“黑魔法”与魔数 (Magic Numbers)**

任何反常识的硬编码、强制延时或针对特定硬件/协议的 Work-around 必须注释来源。

- ✅ 正确：`delay(5); // 必须等待 5ms 让传感器 ADC 稳定，参考数据手册 P12`
- ✅ 正确：`if (status == 0x3F) // 0x3F: BIT0~BIT5 全部置位，表示所有通道均已就绪`

**规则 3：为逻辑代码块提供 “段落标题”**

当函数较长或包含多个子步骤时，在每个子逻辑块上方写一行概要，便于扫读。

- ✅ 正确：`// --- Phase 1: 初始化 DMA 通道 ---`

**规则 4：标记 “雷区” 与待办事项**

对于不完美、有潜在风险或性能妥协的代码，使用标准前缀大方标注。

- ✅ 正确：`// FIXME: 当前未处理缓冲区溢出，高并发下可能触发 HardFault`
- ✅ 正确：`// NOTE: 此处的计算故意丢弃了小数部分，以换取 DSP 处理速度`

**规则 5：变量声明旁只注释 “度量单位” 或 “特殊约束”**

- ✅ 正确：`int timeout_ms; // 单位：毫秒 (ms)`
- ✅ 正确：`uint8_t tx_buffer[64]; // 必须 4 字节对齐以满足 DMA 传输要求`

## 4. 文件头注释规范 (File Header Comments)

文件头注释是整个代码模块的“微型 README”，用于描述该文件的宏观架构作用、硬件依赖或系统级假设。严禁在文件头维护修改记录 (Changelog)、作者或日期。

### 4.1 核心标签与规范
*   `SPDX-License-Identifier`: (首行) 使用标准的 SPDX 标识符声明开源协议，拒绝长篇大论的版权文本。
*   `@file`: **必须包含**。只有包含此标签，Doxygen 才会解析该文件。**建议不要跟文件名**（防止重命名文件时忘记改注释），直接写 `@file` 即可。
*   `@brief`: 一到两句话概括该模块在整个系统中的职责。
*   `@details`: (可选) 详细描述。常用于声明：
    *   **硬件依赖**（如：依赖 TIM1 输出 PWM，依赖 DMA1_Channel3）。
    *   **并发/中断安全假设**（如：本文件内所有 API 均非线程安全，需在外部加锁）。

### 4.2 文件注释模板示例

以下是一个典型的硬件驱动层的文件头注释示例：
```c
// SPDX-License-Identifier: MIT
/**
 * @file
 * @brief  大功率 H 桥全桥驱动模块 (底层硬件抽象层)
 * 
 * @details
 * 本模块负责管理 4 路 PWM 信号输出以及相关的死区时间控制。
 * 
 * 【硬件依赖】
 * - 依赖高级定时器 TIM1 (CH1~CH4) 及其互补输出通道。
 * - 死区时间配置基于系统时钟频率，若修改系统主频，需重新校准死区发生器。
 * 
 * 【设计说明】
 * 为保证实时性，占空比更新接口未作软件互斥锁处理，若在 RTOS 
 * 多任务环境下调用，需由上层应用保证访问的原子性。
 */

#include "hbridge_driver.h"
// ...
```

*结语：如果删掉注释，接手的人会陷入 “为什么要这么写” 的困惑，那就是极好的注释。*
